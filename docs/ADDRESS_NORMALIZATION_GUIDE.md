# 주소 정규화 가이드 (체크리스트 14)

## 1. 문서 목적

- 보조금 자료, 지자체 공고, 업로드 파일, 나라장터 계약자료에서 주소 표기 차이를 통합하기 위한 기준을 정의한다.
- 본 모듈은 동일 주소를 **확정**하는 도구가 아니라 **"동일 주소 후보"**를 만드는 정규화·매칭 보조 도구이다.
- 공개자료 중심 분석 원칙과 개인정보 최소수집 원칙을 따른다.
- 상세주소는 개인정보 위험이 있으므로 저장·표시를 제한한다.

관련 코드:

- 정규화 모듈: [`src/normalizers/addressNormalizer.ts`](../src/normalizers/addressNormalizer.ts)
- 표준 타입: [`src/types/addressNormalization.ts`](../src/types/addressNormalization.ts)
- 테스트: [`tests/addressNormalizer.test.ts`](../tests/addressNormalizer.test.ts)
- 정책 검사: [`scripts/check-address-normalizer-policy.js`](../scripts/check-address-normalizer-policy.js)

## 2. 정규화 대상

- 보조사업자 주소
- 수급기관 주소
- 수행기관 주소
- 법인/단체 소재지
- 계약상대자 주소
- 발주기관 주소
- 지자체·공공기관 주소
- 단, 개인 주거지 상세주소는 수집·저장하지 않는다.

## 3. 주소 구성요소

| 구성요소 | 설명 | 저장 기준 |
|---|---|---|
| 시도 | 경기도, 서울특별시 등 | 저장 가능 |
| 시군구 | 수원시, 성남시, 고양시 등 | 저장 가능 |
| 읍면동 | ○○동, ○○읍, ○○면 | 저장 가능 |
| 도로명 | ○○로, ○○길 | 저장 가능 |
| 지번 | 산/번지 등 | 필요 시 축약 저장 |
| 건물명 | 공공건물명, 법인 건물명 | 공개자료면 선택 저장 |
| 층·호수 | 3층, 201호, 101동 202호 | 원칙적 저장 금지 또는 제거 |
| 상세주소 | 개인 주거지·동호수 | 저장 금지 또는 마스킹 |

## 4. 정규화 규칙

| 구분 | 원문 예시 | 정규화 기준 |

| 시도 약칭 | 경기 수원시, 경기도 수원시 | 경기도 수원시 |
| 시군구 표기 | 수원시 팔달구, 수원 팔달구 | 수원시 팔달구 |
| 도로명 표기 | 효원로 1, 효원 로 1 | 효원로 1 |

| 괄호 | 수원시 팔달구 효원로 1 (인계동) | 괄호 메모 제거 또는 읍면동 후보로 분리 |

## 5. 개인정보·상세주소 제한

- 개인 주거지 주소는 수집·저장하지 않는다.
- 동·호수, 층, 상세주소는 원칙적으로 반복수급 분석 키에서 제외한다.
- 반복수급 분석은 시도·시군구·읍면동·도로명/지번 수준의 `addressRegionKey`를 우선 사용한다.
- sourceText 또는 원문에는 `sanitizeForStorage`를 적용한다.
- AI 프롬프트에는 상세주소를 포함하지 않는다.
- 주소는 단독으로 부정수급 의심을 확정하는 근거가 아니다.

## 6. 동일 주소 후보 판정 기준

| 판정 | 조건 | 처리 |
|---|---|---|
| strong_match | 시군구 + 도로명/지번 + 기본 번지가 일치 | 동일 주소 후보, 사람 검토 |
| likely_match | 시군구 일치 + 도로명 유사 + 번지 유사 | 검토 필요 후보 |
| possible_match | 시군구 또는 읍면동 일치 + 일부 토큰 유사 | 추가 검토 필요(보조 검토 후보) |
| no_match | 지역 또는 핵심 주소 토큰 불일치 | 병합하지 않음 |
| ambiguous | 주소가 너무 짧거나 시군구만 있음 | 사람 검토 필요 |

## 7. 반복수급 탐지 활용 기준

- `normalizedAddressKey`는 동일 주소 후보 그룹을 만들기 위한 키이다.
- `addressRegionKey`는 개인정보 위험을 낮춘 지역 단위 반복 패턴 분석 키이다.
- 같은 `addressRegionKey`에서 동일 기관명 또는 유사 기관명이 반복되면 검토 우선순위를 높일 수 있다.
- 같은 주소에 여러 단체가 있어도 공유오피스, 공공시설, 복지관, 회관 등 합리적 사유가 있을 수 있다.
- 따라서 주소 반복은 의심 신호가 아니라 **검토 필요 신호**로 표현한다(부정수급 확정이 아니다).

## 8. 정확도 검증 기준

- 테스트 데이터는 가짜 주소로 구성한다.
- 동일 주소 표기 변형 20쌍 이상을 만든다.
- 다른 주소 쌍 10쌍 이상을 만든다.
- 동일 주소 표기 변형의 80% 이상이 strong_match 또는 likely_match로 분류되어야 한다.
- 다른 주소 쌍의 80% 이상은 no_match 또는 ambiguous로 분류되어야 한다.
- 상세주소는 결과 키에 원문으로 남지 않아야 한다.

## 9. 후속 작업

- 실제 경기도/지자체 샘플 데이터로 주소 정규화 품질 검증
- 행정구역 사전 보강
- 도로명/지번 주소 분리 정확도 개선
- 주소 API 또는 우편번호 API 연동 검토
- 업로드 parser 결과에 `normalizedAddressKey` 연결
- G2B 계약데이터 매핑에 `addressRegionKey` 연결
- 사람 검토 UI에서 동일 주소 후보 표시

---

본 가이드는 주소 표기 통합을 위한 보조 기준이며, 동일 주소를 확정하지 않는다. 자동 확정 병합을 수행하지 않으며, 모든 병합 후보는 사람 검토 대상이다. 같은 주소 반복은 검토 필요 신호일 뿐이며, 본 모듈은 주소만으로 부정수급을 단정하지 않고 보상금 지급을 보장하지 않는다.

## 초보자 안내 — 왜 상세주소를 저장하지 않나

- **왜 주소 정규화가 필요한가:** 같은 장소가 도로명/지번, 띄어쓰기, 건물명 차이로 다르게 적히면 "동일 주소 후보"를 못 찾습니다. 시군구+읍면동+도로명/기본번지까지만 키로 만들어 비교합니다.
- **왜 상세주소(층·호·동호수) 원문을 저장하지 않나:** 상세주소는 개인정보·거주정보가 될 수 있어 키와 저장에서 제외하고 `removedDetailTokens`로만 분리하며, 저장 텍스트에서는 `[masked-address]`로 마스킹합니다. 반복수급 분석은 `addressRegionKey`(지역 단위)를 우선 사용합니다.
- **확정이 아님:** 같은 주소 후보도 부정수급 확정이 아니라 검토 신호입니다. 공유오피스·복지관·회관·공공시설일 수 있어 `warnings`/cautionNotes로 표시하고 사람이 확인합니다(`reviewRequired`).
- **다음 위험룰 연결:** `addressRaw → normalizedAddressKey / addressRegionKey`로 연결되어 다음 단계 **동일 주소 다수 단체 룰**의 입력이 됩니다(이번 단계는 전처리까지).
- **실데이터 커밋 금지:** 주소가 포함된 산출물(`data/upload-parser`, `data/collector`, `data/baseline`)은 GitHub에 커밋하지 않습니다.
